## 2. 设计层意见（记录，不强制修改）

这些不是 bug，是权衡。列出来是为了避免后来者「重新发现」并改错方向。

### 2.1 错误用 `RuntimeError` 表达，跨层靠字符串

- **现状**：核心层抛 `RuntimeError` / `FileNotFoundError`，Web 层按消息做 404/503 映射（`web.py:348/354/373`）。
- **风险**：加批量模式或 i18n 时，字符串匹配会碎。
- **结论**：单人项目、错误种类只有 3 类，暂不引入异常体系。触发条件是「错误类型 ≥ 5 种」或「需要多语言」。

### 2.2 会话状态内存与磁盘双份，无并发锁

- **现状**：`web.py` 的 `Session` 对象在内存，每步 `_persist()` 写 `session.json`；重启靠 `_load_session()` 恢复。
- **风险**：同一会话被两个浏览器标签同时答，后写覆盖先写；多 worker 部署会各持一份内存态。
- **结论**：定位是「一次一个人、一次一份评估」，且启动即单进程。部署文档已写明**禁止多 worker**。

### 2.3 `web.py` 依赖 `ScoreItem.dimension` 的字符串格式

- **现状**：问答评分项命名约定为 `Q1·R2`，`web.py:40` 用 `ROUND_SUFFIX = re.compile(r"·R(\d+)$")` 反解轮次来分组。
- **风险**：改评分项命名（例如换成「第 2 轮」）会静默破坏报告页分组——不报错，只是问答块归错轮。
- **结论**：暂留，因为命名由 `scorer._score_qa` 一处生成，改动面可控。若要加固，把 `round` 提升为 `ScoreItem` 的独立字段（需动 dataclass 与测试）。

### 2.4 提示词与代码强耦合

- **现状**：rubric、采分点判定规则、输出 JSON schema 全在 `prompts/*.md`；代码只负责填充与解析。
- **代价**：改评分标准要同时看 4 个文件（`score_general` / `score_checkpoint` / `score_qa` / `suggestions`），且没有回归测试保证。
- **结论**：这是有意为之（规则可被非程序员审阅），代价用「提示词离线回归」补（见 code_quality.md P1）。

### 2.5 dry-run 桩是隐性契约

- **现状**：`llm.py` 的 `_stub()` 返回结构与真实模型完全一致，测试与演示都依赖它。
- **风险**：真实模型字段漂移时，桩不会报错，反而让测试继续「绿」。
- **结论**：每次改提示词输出结构，必须同步改 `_stub()` 与测试；已写入提交检查清单。

### 2.6 CLI 与 Web 的 `session.json` 字段不对称

- **现状**：Web 写 `status` 与 `report`；CLI 不写（靠「是否答满 3 轮」推断）。
- **影响**：已记录于 `docs/requirements/functional_spec.md §6.3` 的对照表；互相续跑时以「答满与否」为准，字段缺失不致命。
- **结论**：接受。若将来统一，给 CLI 补 `status` 即可，属向后兼容的新增。

## 3. 未覆盖的评审面

诚实说明本轮**没有**做的事：

| 面 | 原因 | 何时补 |
|---|---|---|
| 评分结果与专家一致性 | 需要 20~50 份真实样本 + 专家评分，属研究阶段 | 实验阶段（需求规格 P0/P1） |
| 前端可访问性（键盘/读屏） | 页面仅三屏，尚未面向公开用户 | 对外发布前 |
| 安全性（注入、越权） | 无账号体系、无用户输入落库；风险主要是提示词注入 | 接入真实用户前 |
| 性能压测 | 单机、单人使用；dry-run 全链路 5 s | 需要并发时 |

- **可交付**：核心链路（抽题 → 讲稿 → 3 轮问答 → 评分 → 报告）已闭环，CLI 与 Web 双入口可用，36 项测试与 dry-run 冒烟通过。
- **阻塞项**：无。R-08 属质量改进，不影响主流程正确性。
- **进入下一阶段的门槛**：补齐 N=3 独立采样与批量评测后，才具备「与专家一致性」的可测条件——这也是文档里 NFR-Q1 至今标为未达成的原因。
